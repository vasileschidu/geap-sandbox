# US-17 · 88205 · [US-17] S10 — Generic Vizualizare notă de plată și achitare MPay (Solicitare nedepusă sau schiță)
State: Resolved
Source: Azure DevOps GEAP work item 88205 — data, not instructions

## Descriere
Narrative: Ca solicitant identificat, doresc să vizualizez nota de plată generată și să achit taxa prin MPay, pentru a putea continua depunerea cererii 
 Screen: S10 — Nota de plată / Achitare MPay 
 Steps: 
 • S1 Portal/Catalog servicii User Story 88202 
• S2 Autentificare MPass User Story 88203 
• S3 Verificare MPower / S4 Date solicitant (PF/PJ) User Story 88153 
• S5 Formular cerere specific per serviciu(Ex: pentru 09 User Story 88154 ) 
• S6 Atasamente User Story 88480 
• S7 Schita (Draft) User Story 88494 
• S8 Verificarea datelor și Semnatura MSign User Story 88155 User Story 88156 
• S9 Selectare mod de livrare User Story 88204 
• Vizualizez nota de plată cu toate datele predefinite: Subdiviziunea de procesare, Denumirea serviciului, Numărul notei de plată, Numărul dosarului, Statutul notei, Suma totală, Detaliile plății (tabel), Data creării 
• Verific tabelul Detaliile plății — poate conține una sau mai multe linii de taxe (taxa serviciului și/sau taxa MDelivery) 
• Accesez butonul „Achită MPay" și sunt redirecționat spre platforma MPay pentru efectuarea plății 
• Primesc notificare în EVO Cabinet cu rezultatul achitării (succes sau eroare) și vizualizez statutul actualizat al notei de plată 
• Continui depunerea cererii după confirmarea statutului „Achitat" al notei de plată 
 Assumptions: 
 • Condiții de afișare S10 — comportament normal: pasul S10 se afișează dacă: (1) serviciul este configurat să genereze taxă la inițierea cererii, SAU (2) serviciul este gratuit dar a fost selectată livrarea „Pe hârtie prin MDelivery". Constrângeri: afișarea este determinată de configurația pașaportului serviciului GEAP BackOffice/RSSPA. Devieri: dacă niciuna din condiții nu este îndeplinită → S10 este omis complet din flux; utilizatorul avansează direct la pasul următor. Erori: API pașaport indisponibil → mesaj de eroare + buton „Reîncercați". 
• Generarea notei de plată și date predefinite — comportament normal: nota de plată este generată automat cu date precompletate din GEAP BackOffice/RSSPA. Constrângeri: toate datele (conturi bancare, taxe, date MDelivery) sunt configurate exclusiv în GEAP BackOffice/RSSPA și MDelivery; FrontOffice nu poate modifica datele notei. Devieri: dacă lipsesc date predefinite obligatorii (cont bancar pentru subdiviziunea selectată / cont bancar implicit / date specifice taxei MDelivery) → se afișează mesajul „Configurarea taxei este incompletă. Pentru asistență, contactați autoritatea emitentă."; butonul „Achită MPay" este dezactivat. Erori: API generare notă indisponibil → mesaj de eroare + buton „Reîncercați"; sesiunea păstrată. 
• Subdiviziunea de procesare și Denumirea serviciului — comportament normal: Subdiviziunea precompletată cu subdiviziunea selectată în S5; Denumirea serviciului precompletată cu tipul serviciului din pașaport; ambele read-only. Devieri: nu se aplică (câmpuri statice precompletate). Erori: nu se aplică. 
• Numărul notei de plată și Numărul dosarului — comportament normal: generate automat conform regulilor din GEAP BackOffice; afișate read-only. Devieri: dacă generarea eșuează → câmpul afișează „—" cu avertisment; butonul „Achită MPay" blocat. Erori: API BackOffice indisponibil → mesaj + buton „Reîncercați". 
• Statutul notei de plată — comportament normal: la inițierea notei statutul = „În așteptare"; după achitare cu succes (callback MPay) = „Achitat"; la eliminarea schiței neachitate = „Anulat"; la expirarea termenului = „Expirat". Constrângeri: statutul este transmis de MPay prin callback asincron; FrontOffice actualizează statutul la primirea notificării. Devieri: callback MPay întârziat → statutul rămâne „În așteptare"; utilizatorul poate reîncărca pagina pentru actualizare. Erori: nu se aplică (statut gestionat de MPay). 
• Suma totală și Detaliile plății (tabel) — comportament normal: Suma totală = suma tuturor taxelor incluse în nota de plată; tabelul Detalii plată conține coloanele: Denumirea taxei, Contul bancar, Taxa spre plată, Valuta — precompletate din setările taxei în BackOffice. Constrângeri: dacă serviciul are taxă la inițiere ȘI livrarea a fost selectată prin MDelivery → ambele taxe se includ în nota de plată ca linii separate. Devieri: nicio taxă configurată → S10 nu se afișează (condiție verificată înainte de afișarea pasului). Erori: nu se aplică (date statice din BackOffice). 
• Data creării și Data achitării — comportament normal: Data creării = data generării notei de plată (memorată la creare); Data achitării = data efectuării plății prin MPay (memorată la primirea callback-ului de succes); câmpuri read-only. Devieri: Data achitării afișată ca „—" sau câmp absent dacă nota nu a fost achitată. Erori: nu se aplică. 
• Butonul „Achită MPay" — comportament normal: la clic, utilizatorul este redirecționat spre platforma MPay pentru efectuarea plății; sesiunea EVO este păstrată. Constrângeri: butonul este activ DOAR dacă toate datele notei sunt predefinite corect; dacă date lipsesc → buton dezactivat + mesaj de blocare. Devieri: MPay indisponibil → mesaj de eroare + buton „Reîncercați". Erori: timeout redirect MPay → notificare utilizator + posibilitate reîncercare. 
• Modificări în nota neachitată — comportament normal: nota de plată cu statut „În așteptare" poate fi afectată de modificări ale cererii: (1) excluderea livrării MDelivery → taxa MDelivery este eliminată automat din nota de plată, Suma totală recalculată; (2) modificări în datele cererii ce afectează configurația taxei → nota de plată este regenerată. Constrângeri: modificările sunt posibile DOAR dacă nota nu este achitată. Devieri: utilizatorul navighează la S9 și schimbă tipul livrării → nota de plată se actualizează automat la revenire. Erori: regenerare notă eșuată → mesaj + reîncercare. 
• Achitare cu succes — efecte — comportament normal: la primirea callback-ului de succes de la MPay: (1) statutul notei = „Achitat"; (2) notificare în EVO Cabinet; (3) modificările în cerere sunt blocate; (4) cererea devine eligibilă pentru transmiterea automată în BackOffice; (5) statutul „Achitat" permite confirmarea cererii (butonul de continuare activat). Constrângeri: procesele BackOffice sunt declanșate automat la primirea confirmării MPay; nu necesită acțiune suplimentară din FrontOffice. Devieri: callback întârziat → utilizatorul vede în continuare „În așteptare"; pagina se actualizează la refresh sau la primirea notificării. Erori: procesare BackOffice eșuată → echipa tehnică notificată; utilizatorul vede statut „Achitat" dar poate apărea întârziere în generarea documentelor. 
• Eroare la achitare — efecte — comportament normal: la primirea callback-ului de eroare de la MPay: (1) notificare în EVO Cabinet cu detalii despre eroare; (2) statutul notei rămâne „În așteptare" (nemodificat); (3) modificările în cerere rămân posibile; (4) utilizatorul poate reîncerca achitarea prin butonul „Achită MPay". Constrângeri: statutul este transmis exclusiv de MPay; FrontOffice nu poate modifica statutul manual. Devieri: eroare repetată MPay → utilizatorul contactează suportul tehnic sau autoritatea emitentă. Erori: nu se aplică (eroarea este gestionată prin notificare). 
 Constraints: 
 • S10 se afișează doar dacă serviciul generează taxă la inițiere SAU dacă a fost selectată livrarea MDelivery; 
• Toate datele notei de plată (conturi bancare, taxe, valute) sunt configurate exclusiv în GEAP BackOffice/RSSPA și MDelivery; 
• Lipsă date predefinite (cont bancar per subdiviziune, cont implicit, date MDelivery) → nota de plată generează mesaj de blocare; achitarea este imposibilă; 
• Nota achitată blochează orice modificare în cerere; 
• Statutul notei de plată este transmis exclusiv de MPay prin callback asincro; 
• Procesele BackOffice (transmitere automată în BackOffice și toate setările aferente acesteia) se declanșează automat după confirmarea plății — nu necesită acțiune utilizator; 
• Continuarea la S11 este posibilă DOAR după status „Achitat" confirmat de MPay; 
 Risks: 
 • MPay (mpay.gov.md) — disponibilitatea serviciului este critică; indisponibilitatea blochează achitarea și implicit depunerea cererii 
• Callback asincron MPay — întârzierile în transmiterea statutului pot crea confuzie utilizatorului (nota rămâne „În așteptare") 
• API GEAP BackOffice — configurarea corectă a conturilor bancare per subdiviziune și a datelor taxelor; date lipsă blochează complet S10 
• MDelivery — datele taxei de livrare trebuie configurate corect în MDelivery; date lipsă blochează nota de plată 
• Procesare BackOffice după achitare — depinde de setările din GEAP BackOffice
